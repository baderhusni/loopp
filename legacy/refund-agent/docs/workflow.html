② The agent decision loop

1
Verify the customer find_customer
Look up by email; refuse to act on an account that isn't theirs. A bad email returns an error step → the agent asks again.
2
Fetch the order get_order
Pull the items: price, quantity, final-sale flag, refunded flag, delivery status.
3
Check the policy check_refund_eligibility
The deterministic policy engine returns a verdict + the exact rule. Every decision — even a denial — is grounded here.
APPROVE
issue_refund  re-checks the policy, then records the refund.
ESCALATE
escalate_to_human  opens a ticket: >$500, undelivered, or defective final-sale.
DENY
Explain the decision and the specific rule, politely and firmly.
4
Reply & record the trace
State the outcome + the rule. The full run (tool I/O, reasoning, latency, tokens, cost) is saved to the admin trace.
🛡
Defense in depth — why pleading & prompt injection fail. The policy is enforced in the prompt and inside the tools: issue_refund runs the same policy engine and refuses any non-APPROVE verdict. So a customer can make the model try a refund, but the tool will not perform it — the prompt is the soft layer, the code is the hard guarantee. Verified live: injection → DENIED, zero refunds recorded.
